# Ordinary POS checkout projection contract

This reviewable patch targets payments commit `434f3e438d1cb48c64e5723222c6efda506db571`. It is saved in `../patches/payments-pos-checkout.patch`, with its SHA-256 in `../ordinary-manifest.json`. The sibling source checkout is unchanged. The patch has not been deployed and no live order, payment, notification or database write was used for verification.

The original `juspay/Order.go` dispatches ordinary confirmation asynchronously for prepaid orders. `juspay/model.go:2037` publishes order/payment status before wallet and stock changes, ignores several database errors, uses a global connection for some writes, and starts network effects before all work has succeeded. The same confirmation method is called by `payment.go` and `amount_check.go`; protecting only the HTTP entry would leave those paths unsafe.

## Atomic boundary

The patch routes ordinary POS HTTP confirmation and every POS `OrderAndStockConfirmed` callback through `internal/poscheckout.Confirm`. Online orders keep their original confirmation body. The engine locks the order, its unique receiving store/counter, exact lines, customer wallet, redeemed voucher and store stock. It rejects legacy placed/paid orders without a matching proof instead of repeating their deductions.

`transform_source.go` extracts the pinned allocation statements using Go's parser. Their amount expressions, float32 conversions, cent rounding, FIFO priority, voucher/coupon history, membership behavior and donation allocation remain source owned. It binds all writes to the caller transaction, propagates SQL errors and removes network/goroutine/logging code from that transaction. Conditional stock updates prevent negative stock. A callback panic, SQL failure, changed line, incomplete wallet allocation or failed proof write rolls everything back.

The proof header and every exact line commit in that same transaction, before success is published. Native MySQL `JSON_OBJECT`/`SHA2` expressions are shared verbatim with `src/modules/checkout/projection.ts`; application numeric serialization is excluded. Header proof includes order/customer/payment method and source monetary allocation inputs. Explicit columns bind receiving store/counter/customer; line proofs bind exact has-product ID, SKU, quantity and stored price. Status and invoice timestamps are excluded because subsequent payment and invoicing update them. There is no automatic proof backfill.

HTTP success remains HTTP 201 with `{"status":201,"message":"/thank-you"}`. A replay validates the current proof and never debits wallets, stock or effect jobs again. The original authenticated customer ownership check still runs. Ordinary HTTP confirmation also requires `X-POS-Projection-Key`, checked in constant time against `POS_CHECKOUT_PROJECTION_KEY` (at least 32 bytes). The rewrite forwards its matching `TSS_POS_CHECKOUT_PROJECTION_KEY` only to confirmation. `X-POS-Operator-ID` carries the initiating operator for correlation; it grants no authorization. Nested transactions fail closed rather than committing work owned by another caller.

## Explicit integrity and security corrections

- Nonzero legacy `CashbackUsed` is rejected before mutation. Its original branch reads `tss_money` but writes `cashback`. That branch remains in the pinned oracle for review; it is not silently reinterpreted or enabled.
- The customer row is locked before both fresh confirmation and proof replay. Current `status=1`, `is_block=NULL/0` and `is_disabled=NULL/0` are required; inactive, blocked, disabled or corrupt flags fail before source mutations. Nullable flags use `sql.NullInt64`. Node confirmation/projection/payment checks independently use writer locking reads, and a block during a provider charge freezes completion without dispatching that charge again. Cached API-v2 auth-user context cannot authorize this boundary; quote/profile cache coherence remains a separate rollout gate.
- Money, points, voucher value and employee coupons require a private purpose-bound customer consent proof before source allocation. The exact contact revision/digest, order/customer/original operator/store/counter and fixed OTP expiry are bound by a domain-separated HMAC. All orders write a consent attestation, including cash-only required-zero rows, in the projection transaction. After source application, the native final monetary/coupon header must equal the locked original header: a late employee-coupon or amount change rolls back every effect. Committed replay verifies the immutable attestation without requiring another OTP or reinterpreting a later contact change. See `../../../parity/checkout-customer-verification.md` for the complete wire/recovery contract.
- A customer aggregate balance without sufficient source earning-history allocation is rejected and rolled back. The allocation total is checked using the original float32/cent boundaries. Such legacy data needs audited repair; this rejection is an intentional integrity correction, not a source-success parity claim.
- Unset expiry on negative money/point debit rows is omitted so MySQL stores its verified `DATETIME NULL DEFAULT NULL`. The original zero Go time fails strict MySQL as a zero date. Only this database-format shim is also used in the isolated oracle; monetary expressions are unchanged. SQL mode is never weakened.
- Purchased gift cards stay disabled while cash-on-counter payment is pending. Prepaid orders lock/recheck batch readiness and record immutable per-voucher activation proof in the same paid/stock/proof transaction. Pending checks enforce readiness; completed replays retain funded value after a later batch block/redemption. See `../gift-card.md` for v2 creation/funding fencing.
- Membership SKUs require the actual API-v2 staged before-state proof and native all-writer revision fence. Original Go activation upgrades the same proof atomically with the projection, retaining the true prior entitlement/expiry; immutable completed replay never reactivates a later changed membership. The real Python→Go→Node bridge, eight source writer differentials, separately reviewed trigger/index rollout and v2 contract/key/manifest prerequisites are in `../pending-cancellation/membership-producers.md`. Missing historical provenance cannot be backfilled from current membership.
- POS no longer clears the original unbound Redis `txn_lock_<customer>` flag. That key is shared with other flows and contains no ownership token. Existing locks expire using their original TTL. The mutation is never replayed as an effect.
- Request, body, customer identity, SQL errors and credentials are not logged by this adapter. Individual delivery logs retain static module/resource/event IDs, a unique event instance, initiating request ID and operator ID.

## HTTP logging boundary

The pinned application uses `gin.Default()` and installs another `gin.Recovery()`. Gin 1.11.0's recovery request dump masks only `Authorization`; its debug panic and broken-connection paths can expose a private projection header, cookies and query values. The composed patch replaces both defaults with `gin.New()` plus `poscheckout.PrivateHTTP`. That middleware emits a closed JSON event schema containing static module/resource/event IDs and validated request/operator correlation. It never formats a URL, header, body, recovered value, raw error or stack. It validates the independent projection key once, removes its raw header before subsequent middleware, and keeps only a request-scoped authorization bit. Customer JWT ownership validation remains independent.

The audit includes `main.go`, `auth/Auth.go`, the `authUserID` helper, the entire `ProcessOrder` prefix through the POS adapter, the adapter, transaction callback and effect worker. Authentication parser/verification errors and JWT subjects are replaced with static events. Pre-adapter order ownership/retry logs are removed or replaced with static events; their cloned ORM handles disable query/error logging without changing the global handle. The composed exchange delivery logger uses the verified initiating operator (or null), rather than the customer ID, and omits order data.

This is a scoped POS confirmation privacy correction. It does **not** certify every legacy service handler: for example `CreateCustomer`, refund/provider handlers, webhook middleware and unrelated cron paths retain separate logging that must be reviewed before they are exposed or incorporated into a new contract. The normal POS adapters return before `CreateCustomer` and the old asynchronous source branches. Activation remains gated on the deployed composition and remaining service-path audits.

## Durable postcommit effects

`ordinary/migration.sql` creates `pos_rewrite_checkout_projection_effects`. Source inventory sync, engagement, producer, order email, gift email/check, membership welcome, UTM and freebie payloads are queued transactionally with the projection. Only a newly committed projection enqueues jobs. The standalone `cmd/pos-checkout-effects` worker claims jobs with `FOR UPDATE SKIP LOCKED` and publishes their safe outcomes. A job is marked processing before dispatch; interrupted/unknown delivery remains frozen for reconciliation. It never blindly retries a possible external side effect. Missing endpoint or producer credentials leave that resource pending rather than reporting success.

The worker uses the original configured service endpoints, validates HTTPS, rejects redirects and bounds time/body size. A source effect is separate from proof that stock and wallets committed. Delivery approval and provider-specific idempotency/reconciliation remain operational dependencies.

## Isolated verification

Run from `backend`:

```sh
python3 compatibility/upstream/ordinary/prepare_source.py
python3 compatibility/upstream/ordinary/prepare_patch.py
python3 -m unittest discover -s compatibility/upstream/tests -v
sh compatibility/upstream/ordinary/run-isolated-tests.sh
python3 compatibility/upstream/ordinary/compile_payments.py
```

Both generators are read only by default; `--write` explicitly regenerates reviewed artifacts. The SQL harness creates a fresh, portless MySQL 8.4 container and refuses every other DSN/schema. Its race-enabled tests execute the extracted original allocation oracle and actual patched Gin adapter without starting the upstream application. They cover float32/FIFO rounding, wallet/stock contention, 20 same-order and callback retries, private-key rejection, paid prepaid/card activation, source voucher/coupon/membership/donation behavior, incomplete earning history, proof tampering, injected SQL errors, callback panic, atomic rollback, and frozen uncertain delivery. Privacy tests execute the actual patched source authentication middleware and both Gin modes with success/rejection/panic/broken-pipe paths and secret/cookie/customer-query/body/JWT/raw-error canaries. All fixture identities and credentials are synthetic. The compile script applies both exchange and ordinary patches to a disposable archive, then builds the actual application, `juspay` package and worker using pinned Go 1.25.4. It never starts them.

## Activation requirements

1. Confirm the deployed payments revision and review the pinned patch, including the deliberate corrections above. A source commit alone does not certify the deployed service.
2. Apply `src/modules/checkout/migrations/0009_checkout_projection_proof.sql`, `src/modules/checkout/migrations/0015_gift_card_issuance.sql`, `src/modules/checkout/migrations/0017_customer_consent_proof.sql`, `src/modules/customer-contacts/contact-revisions-migration.sql` and `ordinary/migration.sql` through the controlled migration role. `ordinary/customer-consent-migration.sql` is the exact shared0017 copy. Grant proof writes only to the patched transaction; the rewrite reads ordinary proof through its writer connection and writes per-voucher issuance proof only with confirmed local counter settlement. Keep migration privileges separate.
3. Audit and serialize every other writer of the same customer wallets, earning histories, vouchers and store stock before activation. Locking this service cannot prevent an unpatched writer from computing a stale balance outside the shared row lock and later overwriting it. This remains a production prerequisite.
4. Configure the shared private key, verified `UPSTREAM_POS_CHECKOUT_PROJECTION_CONTRACT=pos-checkout-projection-v1` and `UPSTREAM_POS_CUSTOMER_CONSENT_CONTRACT=pos-customer-contact-consent-v1` in the rewrite, and configure the dedicated effects worker. Verify sandbox permissions, source allocation history quality, lost-response recovery and actual endpoint contracts. A positive header/flag alone is not acceptance evidence; the writer transaction must produce matching native attestations.
5. Reconcile historical paid/placed orders lacking proof through an audited repair process. Never fabricate proof from paid status, an HTTP acknowledgment, a current wallet/stock balance or a draft. The rewrite keeps those sales incomplete until authoritative completion is proved.

Live provider certification, legal invoice approval, return stock restoration and the complete feature/route parity gate remain separate requirements. This patch does not claim production readiness for those dependencies.
