# Store and operator archive lifecycle: user clarification

The user clarified that Store/PosUser records are not physically deleted in the active application: they are marked archived/deleted so they cannot access it. **Preserve the existing reversible flag/archive lifecycle and reactivation semantics.** Retain numeric rows, the PosUser→MUser mapping, store/counter IDs and all financial/audit history. Archived operators lose online access; archived stores reject new operational work. Already collected signed offline cash remains recognizable for manager review. No permanent retirement, non-reactivation tombstone, new physical-delete route or ID reuse is introduced.

The earlier permanent-retirement proposal is superseded. No further deletion behavior choice or live deletion approval is pending. Generic inherited Django hard deletion is recorded below as an observed framework capability, rather than a required active Store/PosUser business flow.

The concrete source evidence is `tools/administration-history/collector-oracle.py` and `parity/administration-delete-inventory.json`, pinned to Django4.2.5 framework file hashes and source commit `78d5b63d6a149a6bf2c748fa1d191799c59ecb8a`:

- All8 explicit source Store relations use `DO_NOTHING`. The native framework experiment omits such children from the confirmation collector; with a physical FK it raises IntegrityError, and without one it deletes the parent while leaving the child. Plain integer references are also invisible and survive as orphans. Source models contain at least20 scalar Store references, including returns, terminal transactions and day-close/banking/opening balances.
- Deleting a User through the inherited collector removes that user's authored Django administration logs through CASCADE. The source UserAdmin also allows self deletion when that user is the last superuser; the pinned experiment deletes the account and its authored logs.
- A failed constrained single deletion rolls back both deletion and its log. The inherited bulk action instead leaves a committed deletion log even though the target still exists. The replacement Group bulk implementation uses one transaction and one durable receipt, including authentication revocation, to avoid this false audit outcome.
- The supplied reader's visible inbound graph has no Store/PosUser FKs, and its history user FK actually points to `auth_user`, not the source-configured `PosUser`. Missing visible constraints do not prove there are no application references, nor that this is the operational auth writer. Existing history provenance and actor-binding gates remain required.

The replacement adds further identity retention requirements. Signed receipts can exist only on a signed-out device and arrive after deactivation. An empty server receipt/grant query is therefore insufficient proof that an ID is unused. Offline manager handoff verifies the original actor fingerprint, retained signing key and original operator/MUser/store/counter binding; removing those rows can prevent recognition of cash already collected. Payment/return outboxes, fiscal line/refund/credit-note history, day-close versions and reports/fulfillment command snapshots also retain IDs in JSON without physical FKs. Parent-row lock order must remain operator/check-in before Store/Order/SKU; a deletion guard that takes locks in the opposite order introduces a separate concurrency problem.

Physical deletion is outside this clarified business scope. A complete reference/fencing analysis would still be required before any future change: absence of visible FKs, current server receipts or active sessions cannot prove an identity unused, because signed-out devices and external producers remain. Keep source actor-domain gates intact; commerce MUser IDs must not be joined directly as PosUser IDs. This inventory documents those hazards without authorizing a destructive implementation.

GroupAdmin deletion is independent: it removes reconciled group memberships/permission assignments while retaining operator accounts and all financial identities. Bounded selected-group preview/deletion can therefore proceed using the already verified rewrite grant graph, with current internal superuser permission, optimistic versions, atomic receipts and permanent authentication revocation. Operational legacy access import remains a deployment gate.

The implemented active lifecycle remains archive/deleted flags plus explicit reactivation. No Store/PosUser permanent-delete or permanent-retirement implementation is required by the clarified request.
