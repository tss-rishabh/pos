# Store and online order transaction evidence

Source baseline: `backend-pos-web` commit `78d5b63d6a149a6bf2c748fa1d191799c59ecb8a`. `order-report-sql.ts` records extracted source SQL and its SHA-256; the former `tools/operational-reports/generate-order-report-sql.py` (removed 19 November 2026; output frozen) regenerated that manifest and the frontend's 75-column manifest from the source. No source database or fulfillment API is called by this tool.

`POST /api/v1/reports/order-transactions/search` and `OrderTransactionsPage({user,storeId})` cover store and online sales plus returns. Filters select an inclusive business-local timestamp range, explicit stores, source and order-date/return-date basis. All authenticated source roles are supported; non-superadmins require assigned stores, and restricted user type 2 retains that boundary even with role 1. An empty selection returns no rows. The export queue's `order-transactions` kind produces the complete filtered 75-column CSV.

The query compiler binds store and date values, validates parsed aliases and supports strict MySQL grouping with explicit `ANY_VALUE` for source non-grouped projections. Refund amounts retain MAX, duplicate source transaction-ID projections retain the final identical field, and numeric/string/NULL constants remain constants. Count queries omit label-only category joins and expensive projections while preserving selection and grouping. The source's four branches and their distinct sale/return date predicates remain separate. Order/store, product, payment, tax, points, discounts, refunds, staff, GST registration, invoice and credit-note fields retain their source calculations.

The formatter reproduces Python float rounding, whole-number ties-to-even and string formatting. It preserves the source's unusual negative individual-points branch when store PG discount is nonzero: `total_sale` may remain an unsigned, unrounded number for a return. This behavior is documented rather than silently changed. Source non-grouped labels are ambiguous when joined rows disagree; explicit ANY_VALUE preserves that ambiguity. Fixture parity does not certify those labels across arbitrary production query plans. Lossless IDs use strings, dates are normalized, and CSV formula escaping/BOM are deliberate security/encoding differences from raw legacy bytes.

Current-business-day order-date cohorts use the data reader. Return-date cohorts always use BigQuery because the joined original sale can be older; historical/mixed order-date cohorts also use BigQuery. Both matching views are required from this validated configuration:

| Source | Sales view | Return view |
|---|---|---|
| Store | `BQ_STORE_ORDER_SALES_VIEW` | `BQ_STORE_ORDER_RETURNS_VIEW` |
| Online | `BQ_ONLINE_ORDER_SALES_VIEW` | `BQ_ONLINE_ORDER_RETURNS_VIEW` |

Each compatible view must expose every raw alias in `orderReportLineSchema` and `orderReportProjection`, plus `source_store_id`, `sale_created_at`, `return_created_at`, `line_item_id`, `refund_order_id` and `refund_product_id`. It represents pre-group rows from the corresponding extracted source branch, including its source status/payment/category/return exclusions and CASE expressions. DATETIME values are business-local, IDs are lossless, and numeric projection types must match the runtime schema. The API applies bound time/store filters before grouping by the last three keys, computes MAX for `PayAmountRefunded` and ANY_VALUE for other aliases, unions sales and returns, then sorts and pages. The return-date choice uses the source's return-event timestamp; sales always use sale creation. No MySQL historical fallback exists. Warehouse requests carry resource label `order-transactions`. Views, ingestion time semantics and reconciliation against approved production data remain release gates.

Evidence: 49 fixtures execute the actual Python formatter and compare 50 resulting rows and all 75 source CSV headers. Isolated MySQL fixtures construct 23 tables from verified physical column metadata, execute all four source selection combinations and compare the bound strict-grouping implementation, including old sales with current returns, online allocation dates, category priority 153, source refund selection and store scope. Separate tests check query compilation, warehouse bindings/routing, missing configuration and export limits. The 70,000-row guard bounds complete exports. These checks establish source-derived fixture parity, not full production-data, performance or desktop acceptance certification.
