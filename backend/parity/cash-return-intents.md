## Return protocol and authority

A writer transaction first saves `PREPARED`, reserving the financial correction UUID, original payment UUID, unique cash-return receipt UUID, exact net amount, original native funding hash, whole-order snapshot, source order/funding dates, business timezone, preparer, request ID and purpose-bound original session hash. No physical cash instruction is permitted by preparation. Current manager role1–3, active operator, current store assignment/franchise category, current check-in, original counter and valid non-revoked epoch-bound POS session are checked. Row locks follow current identity/check-in → Store → Order → intent/payment rows.

A separate original-UUID arm command rechecks source eligibility and the mandatory injected handover/import barrier under the same Store→Order locks. It commits `RETURN_PENDING` and an authenticated pending financial control before acknowledging. Only the first successful arm response has `newlyArmed:true`. Replay, GET, reload, another manager and lost-response recovery never grant another handback permission. The client persists its original action before dispatch and consumes the presentation permission before displaying it. Browser-storage failure prevents dispatch/presentation.

The operator attests cash **already returned**, with its original physical handler, UTC instant and frozen business timezone/date. The original armed session is required for an own-return attestation; another currently authorized manager can record a reviewed original return. Attestation never reruns a now-stale fulfillment decision and thereby loses a real physical fact. It leaves the cash unresolved as `ATTESTED`. The financial correction later rechecks all ordinary native funding, projection, line, issued-value, source snapshot and inverse-handover proofs, appends one correction/money pair and marks the intent `RECORDED` in the same transaction. The financial receipt/commands/comments retain the real resolving actor separately from the original handler and attester.

An actual 23:59:59.500 handback remains an outflow of that business day when another manager records it after midnight or the original operator signs out/is archived. `recordedAt`/`recordedInstant` describe financial recording, not a replacement cash-out date. The original paid attempt JSON, delivered comments and projection/benefit/stock proofs remain unchanged. No provider refund, fulfillment effect, restock, wallet, voucher or membership mutation occurs. For a ₹100 sale with ₹150 originally received and ₹50 already given as change, this records ₹100 returned, never ₹150.

Only an unarmed `PREPARED` intent can be cancelled, with an explicit no-cash-return attestation, reason, evidence UUID and current manager audit. Arm-vs-cancel is serialized; one wins. An armed, uncertain, attested or retained cash return cannot be cancelled. If physical facts or source funding/fulfillment cannot be reconciled, the retained return remains visible and figures remain blocked; the application never invents a refund, zero or another cash handback.

## Earlier device journals

Old saved `pos:payment-correction:v1:*` references keep their original financial UUID and exact payload. Missing/500 is not permission to generate a replacement or return cash again. The current store's manager queue can inspect old references retained on that device, including other operators, and explicitly intake an immutable claim with the original handler, actual return time and reviewed evidence. Intake verifies native original cash funding and counter, saves a separate `retained-device` origin, and exposes the claim to other authorized managers/devices. It does not fabricate an earlier PREPARED/armed history. Unknown intake replies recover with GET; the same original ID is retained.

A claim can reconcile the original financial command once. If that exact older correction is already recorded, the adapter verifies its original request binding, sealed receipt, funding and exact money pair before linking it; it creates no second correction or outflow. A conflicting original date/handler/amount/reference is retained for explicit reconciliation, rather than silently rewriting frozen history. The original device reference is cleared only after matching financial receipt evidence; a failed optional order refresh cannot remove the confirmed receipt from the UI. An unregistered journal on a disconnected/lost pre-upgrade device is inherently unknown to the server: cutover must drain/retain those devices and intake their evidence. New operations cannot enter that condition because preparation precedes handback.

## Financial fences

Armed/attested intents and unresolved retained claims contribute to a signed per-store control with their earliest affected date. Pending returns block final day-close state/submission, affected DSR/ledger ranges and another payment or cooperating whole-order handover for the same order. Unknown SQL/HTTP outcomes retain the same pending state. Late SQL failure rolls the financial correction back while the earlier physical-return fact remains pending.

Every control commits a complete per-day head-set count and authenticated membership digest. Reads verify every bounded member and the signed count; deleting the store head, deleting a day head or changing a head cannot masquerade as an unchanged/zero partition. A never-used store's empty financial state is accepted only after explicit absence of armed/retained/managed financial facts and control leaves is established. Preparation initializes a signed empty control; abandoned unperformed preparations do not require an ever-growing scan to prove financial zero. Each day head also authenticates the count/digest of typed managed-order and cash-movement IDs. Matching replicated heads with omitted whole financial tables, or an omitted outflow/receipt pair, cannot produce zero: the DATA candidates must match that membership before the existing amount/funding/money-pair proofs run. The IDs/counts contain no historical amount/customer facts.

Current daily reports use one DATA transaction, bracketed by writer-authoritative head checks; DATA must present the same complete heads. Current ledger and day-close snapshots have equivalent writer/current-snapshot fences. Lagging metadata or a change during the read refuses the result. No primary money fallback substitutes for a lagging report reader.

Historical money remains in BigQuery. The required contract is `pos-payment-correction-finance-publication-v2`; v1, missing partitions/heads, stale seals or different current heads are rejected. Each sealed partition binds the current day head (DSR) or ordered historical head prefix (ledger), plus an immutable `dataReference` with its own generation/source position/CDC watermark/publication time. A fresh common-barrier qualification can reuse those exact unchanged data facts without rewriting unrelated historical partitions. Qualification generation and data generation are separate; ledger source queries use the latter. `sealPaymentCorrectionAtCurrentControls` binds a complete rectangular scope to native heads before/after sealing. It performs no export/warehouse write. The source publisher still must prove baseline hashes, native movement proofs and its actual common source barrier; possession of an environment literal is not that evidence.
