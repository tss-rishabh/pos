## Deliberate security/data-integrity changes

Administrators cannot elevate themselves or others above their administrative tier. OPM can manage SM/Staff only. Store and organization isolation applies on every relevant administration action. Salesperson assignment replacement preserves stores outside the actor's scope, and a second active store outside that scope produces a conflict. Moving stocked storage is rejected. Active store names cannot be duplicated by reactivating an archived store.

New staff credentials use a Django-compatible PBKDF2 hash with a minimum twelve-character policy. The commerce mirror never receives a plaintext or duplicate staff password. Existing customer-email identity collisions fail instead of silently attaching an account. Ordinary profile updates do not accept arbitrary password replacement; root self-service identity and the separate current-superuser administrative password-reset flow handle that feature with source validators and permanent session revocation. Geo coordinates, typed enums, storage capacities, time values and database column limits receive explicit runtime validation.

These are intentional corrections of unsafe legacy behavior, not assertions of byte-for-byte response parity. Browser-facing REST DTOs replace DataTables/HTML responses; full user-visible parity must be tested at the workflow level.

EDC create/edit/delete now requires an authenticated administrator with access to every affected store; the source function views lacked those local guards. Existing credentials are never sent to the browser and an omitted replacement preserves the current credential. Moving a terminal refreshes its store name and first-counter reference rather than retaining source stale metadata. Source name allocation and conflict detection are preserved, including archived machine ordinals; first-counter selection follows source PK ordering including archived counters. Provider secrets retain the existing legacy storage format required by payment integrations; they are excluded from every read projection, response and log.

## Catalog endpoint distinctions

The shared `catalog.ts` implements the POS `AjaxOrderProductsListView` profile. A variant uses its parent price, special price, exclusive price and ERP name. The first GS1 row is selected by its primary key, not the smallest barcode. An own image takes precedence over the parent image, preserving the source CDN string. The query retains stock and archived-parent sellability branches, excludes configurable roots, and supports the source stock toggle and escaped substring search over names, IDs and all barcodes. An `EXISTS` search avoids duplicate outer product rows.

`AjaxCatalogueView` is a different source contract: its bulk caches select the last iterated barcode/exclusive value without a guaranteed row ordering. It must not be marked certified by POS-catalog tests. Held stock, per-storage stock text, DataTables sorting/counts, public catalog payloads and malformed-data edge cases remain outside the shared catalog DTO evidence. Price-list multiple-location tie behavior must be checked on the writer's actual schema/order before full certification.

## Check-in (W8a, C13/C14)
`checkins.ts` uses the legacy Redis keys: `check_in_{uid}` → Python-`json.dumps` text
`[store_id, "store name"]`, EX = `time_until_end_of_day() - 1` in `BUSINESS_TIMEZONE`;
`check_in_list_{store}` → LIST of user ids (LREM from every `check_in_list_*`, LPUSH, EXPIRE).
Check-out writes `[0, ""]` and pushes to `check_in_list_0`, as legacy check-in to store 0. The
optional counter is rewrite-only: `pos:checkin_counter:{uid}` (same TTL). Check-in accepts closed
STORE/CORE_WAREHOUSE stores (`helpers.py:778-791`); operational checks (`assertCheckIn`,
`checkedInStore`) still require an active store, as `get_checkin_store`. Messages: 403 "You are not
assigned to this store"; success "Check-in changed". Store-scope hardening (franchise users only on
assigned franchise stores) is kept. `pos_rewrite_operator_checkins` is no longer used. A check-in
set inside a caller's transaction (login) is written to Redis immediately, not on commit, as legacy.
