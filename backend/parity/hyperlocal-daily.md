# Hyperlocal daily report evidence

Source: `report/datatables/hyperlocal_daily_datatable.py` and `HYPERLOCAL_DAILY_REPORT_QUERY`, baseline `78d5b63d6a149a6bf2c748fa1d191799c59ecb8a`.

`POST /api/v1/reports/hyperlocal-daily/search`, `HyperlocalDailyPage({user,storeId})` and queued export kind `hyperlocal-daily` preserve all 17 source columns, custom report name/notes and asynchronous private CSV retrieval. The API additionally offers a bounded paged preview. Date selection is the inclusive `express_line_item.pending_expires_at` range, not order creation, allocation or accepted expiry. Report groups retain order, user, line, line status, express status and store. Repeated express rows multiply source quantity and amount; amount remains `ROUND(SUM(COALESCE(pre_gst_amt,0)*(1+COALESCE(gst,0)/100)),2)` without a new quantity multiplier.

Earliest ACCEPTED, PACKED, OUT_FOR_DELIVERY and DELIVERED times are calculated across all status-log history for each order/store, including times outside the selected expiry range. The new query batches only displayed order/store pairs (at most 500 per timing query), avoiding the source's full-table lifecycle aggregation. It preserves missing timestamps, old order creation dates and source minute-format CSV dates. Equal sort keys have stable order/line/store/status tiebreakers. Out-of-range pages return page one. Bound store/date values, explicit strict-grouping ANY_VALUE expressions and the common 70,000-row export guard replace interpolated unbounded execution.

All source roles may access the report. Non-superadmins default to their assigned stores and cannot select other stores. Restricted user type 2 retains that boundary even with role 1 and receives server-masked customer names. Internal superadmin may request all stores. The source's configurable unscoped bypass and unmasked restricted-user names are deliberately tightened for security. Export jobs freeze current scope/user type and repeat writer authorization before building and file access; old artifacts never authorize operations.

All nonempty expiry-selected reports require BigQuery, including today, because original order/HP values and earliest lifecycle timestamps can predate the selected expiry day. Configure `BQ_HYPERLOCAL_DAILY_VIEW`, a validated fully qualified compatible view containing one row per source ELI/order/line/store join, with:

`order_id,user_id,line_item_id,sku_id,customer_name,quantity,pre_gst_amount,gst_rate,order_status,line_item_status,express_line_item_status,order_date,store_id,location_code,store_name,pending_expires_at,allocation_date,pack_date,pickup_date,delivery_date`

The four lifecycle fields must already be the all-history minima per order/store; they must not multiply ELI rows. Timestamp columns are business-local DATETIME, IDs are lossless, nullable source labels/times stay null, and numeric values must preserve source float semantics. Bound queries filter expiry/store before source grouping and carry resource label `hyperlocal-daily`. There is no MySQL historical fallback. Production view mapping and timestamp-ingestion reconciliation remain release gates.

Evidence: the actual Python source query is extracted without importing Django and executed against six tables created from verified physical metadata in a fresh, guarded local MySQL schema. The fixture compares all selected fields and tests inclusive endpoints, duplicate express rows, separate statuses, absent lifecycle data, earliest logs before the range, global versus assigned scope and page reset. Warehouse/privacy tests check named binds, resource labels, zero MySQL history reads, missing views, size guards, restricted names and all 17 CSV headers. This establishes deterministic source-query fixture parity, not production-data or byte-identical CSV certification.
