## Remaining release evidence, without inventing missing implementations

1. **One complete multi-client lifecycle acceptance:** log in with real session
   cookies on two clients, issue a valid offline cash grant, disconnect one,
   archive/reactivate the operator or remove/restore its assignment through the
   real administration endpoint, and reconnect. Observe old online cookies and
   pending login proofs denied; old completed receipts remain
   durable and reach manager resolution without repricing, duplicate order or
   new receipt. Existing SQL, browser and cash tests exercise separate seams;
   their presence does not prove this combined workflow. Include role/type
   changes and Store/counter archive with a checked-in stale workspace. Do not
   require instantaneous revocation while disconnected.
2. **Signed installed desktop acceptance on Windows x64 and macOS arm64/x64:**
   restart, logout/account change, upgrade/profile retention and exact trusted redirects.
   Main-process tests and mocked Chromium flows supply security evidence, not
   OS installation/signing/real browser acceptance. `desktop-platforms.md:86`
   and `release-coverage.json` already retain these deployment gates.
3. **Real store printer/storage lifecycle on each mandatory OS:** after offline
   restart and an operator change/revocation, print/reprint the same retained
   cash receipt, then reconnect through stock-conflict manager resolution.
   Browser print interception proves UI invocation, not physical output,
   permissions, printer dimensions, profile retention or signed-app behavior.

These are bounded acceptance gaps, not claims that cash completion or
printing lack runtime implementations. No additional missing runtime connection
was established in this slice beyond the store-status actor race above. The
full original feature ledger and unrelated pending requirements remain intact.
