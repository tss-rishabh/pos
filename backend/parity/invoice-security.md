# Invoice and shopping-feedback security evidence

The concrete unapplied patches, immutable source pins, runtime lock and activation instructions are in [the compatibility runbook](../compatibility/upstream/invoice-security/README.md). These checks establish a bounded transport/credential/logging correction, not full tax/legal, vendor or legacy-route parity.

The original shop invoice GET accepted a query-string secret and created an ordinary customer login token plus `user_token_log` row for its NPS QR. Generic customer auth ignores an added purpose claim. The new resource requires a header-only private service key, and its QR uses a different signing key and strict order-only proof without `sub` or contacts. Separate verification in the actual original customer decoders rejects that capability. The client verifies a nonce- and scope-bound HMAC of exact HTML before sanitizing it.

The invoice worker loads only the pinned controller/models and a reader binding. Real connections enforce read-only transactions, bounded timeouts and unchanged SQL mode. It has no source writer/Redis binding or customer-token helper import. Cache-miss settings behavior is preserved without warming Redis; current database settings instead of stale cached settings must be accepted explicitly in the full template qualification. Fresh writer role/type/store/payment checks both before and after rendering prevent stale operator access without holding locks across an HTTP call.

The isolated feedback service executes original NPS handlers/schemas behind the strict purpose verifier. It bypasses the original main/auth/logging/instrumentation pipeline, replaces relevant source/vendor/database loggers with static events, and does not mount the legacy order-only mutations. Its anonymous proof holder has `userId:null`. The standalone receiver removes fragment credentials before requests, keeps them out of persistent storage/cookies/referrers, renders untrusted labels as text and rejects cross-origin redirects. Unknown submissions remain GET-only and do not falsely prove every source write.

Evidence at this checkpoint:

- 10 independent Python checks cover literal handler execution, whole-module import ordering, source cache-miss values, source-digest startup fencing, private-header/query/ID rejection, key separation/explicit expiry, closed source/Gunicorn errors and 16 concurrent context-variable requests. Node runs these without rewriting artifacts.
- `tests/checkout/invoice-security.test.ts` checks exact Python→Node response/proof compatibility and tampered body/order/operator/request/nonce/purpose/audience/expiry/key cases.
- `tests/checkout/invoice-feedback.test.ts` executes literal original GET/POST handlers and the original generic customer decoders with controlled dependencies. It verifies exact IDs beyond `2^53`, 20 concurrent request correlations, missing/private-key/CORS/size failures, and token/cookie/query/body/database/vendor log canaries. New production entrypoint/verifier/logger code also compiles strictly against typed source seams.
- `tests/checkout/invoice-reader.mysql.integration.test.ts` uses guarded disposable localhost MySQL and the real locked Python 3.12/Falcon 4/SQLAlchemy 2 runtime. An INSERT fails, the existing row remains, SQL mode is unchanged, and the full controller startup exposes only the private resource without writer/Redis-write bindings.
- The independently seeded invoice case in `tests/checkout/mysql.integration.test.ts` exercises protected preview/CSP, exact large IDs, unpaid/cross-store denial, role/type revocation before/during rendering, and substituted HTML rejection.
- Three Chromium scenarios in `frontend/e2e/checkout/invoice-feedback.spec.ts` cover the compiled same-origin receiver/CSP, no URL/storage/cookie/referrer credentials, hostile label text, lost POST/GET-only status, malformed/expired proofs, unsafe redirects and same-tab QR navigation. Existing FastCash and protected-invoice workflows remain separate regressions.

No sibling source was changed, no patch deployed, and no live provider/feedback/message action occurred. Node invoice reads stay disabled without the verified private contracts and key. Full invoice rendering/legal/physical-print parity and source NPS multi-write/concurrency/consumer database qualification remain explicit release gates. Customer-history staff product ratings are a separate feature; neither this verifier nor the read-only NPS report replaces them.

The source order SMS path independently mints customer tokens and puts provider secrets/contact/message into GET parameters. Its existing queue is now held behind a new exact private SMS contract/key and authenticated response proof. The concrete SMS provider correction is still pending; this note does not claim it was implemented or deployed.
