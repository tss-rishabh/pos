## Explicit exchange recovery

- `GET .../line-items/:lineId/exchange-recovery` requires the current receiving-store/counter and verified original customer. It discovers the earlier durable UUID or a retryable original failed log. Read responses contain a revision and minimal recovery state, never provider credentials or original comment/payload.
- `POST .../line-items/:lineId/exchange-recoveries` explicitly claims or adopts the read revision. It has no provider, inbound, refund or inventory effects. Its command hash binds current actor/store/order/line/counter/proof/salesperson and replay body. Pending commands survive a lost response as scoped identifiers; the UI cannot silently choose a new command after an unknown outcome.
- Existing UUID handoff changes only the purpose-specific current authority counter/claim. Ordinary operation authority remains unchanged. Subsequent claimed actions check that operator and fresh proof. Financial counter, existing phase and replacement picks remain intact.
- Original-log adoption locks order/HP/current authority, exact original log, independent credit and native restoration evidence. It requires source retryable HP status, exact old product, same receiving store and quantity, original nonblank credit after the failed log, exact source restoration comment/time/store/product and quantity delta, and no replacement/orphan child. It imports the stored size/reason/comment/saleable choice and asks for a fresh salesperson. It never repeats the original return or stock restoration.
- Original financial counter zero remains zero through payload, child/native stock proof and finalization. It is recorded separately from the valid current authority counter. The original immutable log binding and native credit/stock evidence are checked again before subsequent effects. Retry requires the existing reviewed upstream exchange-stock contract before dispatch.

Missing/extra/ambiguous legacy restoration evidence refuses adoption. The old restoration logs lack HP-line IDs, so identical-SKU multi-line cases may be ambiguous under the current exact-event proof. A complete group conservation proof is a follow-up under investigation; no claim is made that every legacy row is already adoptable. A missing source restoration event is not invented from current stock or handled by repeating an uncertain financial leg. Existing child/uncertain replacement recovery still needs its genuine native/provider proof; this change never fabricates a child acknowledgement.
