# Device sign-in QR handoff

The source `AuthQRGen`, `AjaxGenAuthQR` and `MPosLogin.mpos_check_otp` use POS Redis database0, `auth_qr_<operator_id>`, a 32-character base32 secret, SHA1/six-digit TOTP with a default60-second period and no adjacent window, and secret rotation with a default1800-second TTL after verification. The rewrite retains these values and the decoded QR payload `{email_id,auth_otp}`. It adds a desktop/web profile dialog; no mobile application is being built.

`POST /api/v1/operators/current/device-handoffs` issues or refreshes the signed-in internal operator's QR. `DELETE .../current` revokes the matching revision. `GET .../capabilities` advertises availability. `POST /api/v1/auth/device-handoff-verifications` requires a separate `X-POS-Auth-Key` before parsing credentials. It returns an authentication decision and operator identifier, without creating a browser session or granting POS model/store privileges. The consuming backend must preserve its current-account authorization and session revocation checks.

Explicit security corrections: callers cannot select another operator; disabled, external/franchise or ambiguous-email identities are rejected; current credential fingerprints invalidate old codes; Redis Lua atomically compares and rotates the secret, including a used-code ledger for same-period collisions; account attempts are capped at5 per configured period and the service route at30/minute per trusted client address. Constant-time comparisons protect service keys and codes. Password-only fallback uses the existing normal password/MFA login flow, rather than the source unauthenticated boolean shortcut. `MPOS_QR_TAKE_PASSWORD=true` additionally requires the password when consuming a QR.

QR encoding is local. Codes/PNG credentials remain in the mounted dialog, are cleared when offline or closed, and never enter local storage, persisted query state, external image URLs or logs. Only static resource/event identifiers, request IDs and internal operator IDs are logged. The displayed expiry is bounded by both the source secret TTL and TOTP boundary; source near-expiry codes are never displayed as valid for longer than their Redis lifetime.

The feature defaults off. Configure `POS_DEVICE_HANDOFF_REDIS_URL` (the legacy POS Redis DB0, **not** COMMON_REDIS), TLS for remote/production Redis, a secret-managed `POS_DEVICE_HANDOFF_SERVICE_KEY`, matching source period/TTL/password settings, and `UPSTREAM_POS_DEVICE_HANDOFF_CONTRACT=pos-auth-qr-v1` only after every consuming service has migrated to atomic verification. Legacy direct verification can otherwise race outside the rewrite's protection. No production Redis keys or application configuration were changed.

Validation: `tests/device-handoff.test.ts` executes the pinned source methods with the source-pinned PyOTP2.9.0 across24 secret/period/boundary cases. `tests/device-handoff.mysql.integration.test.ts` starts a private loopback Redis and isolated MySQL schema; eight workflows cover20 simultaneous consumes, Lua CAS, credential/type/status/email changes, password mode, interval expiry, shared attempt budgets, stale revocation, secret TTL and log privacy. Epoch-bound fingerprints also reject a secret after an account field is changed and restored. `frontend/e2e/device-handoff.spec.ts` covers ephemeral UI state, revision-bound revocation, refresh and offline removal. Production consumer acceptance remains pending.
