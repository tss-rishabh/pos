# Inherited model administration history

Two read-only traced APIs and a React page implement the inherited Django history surface behind the single legacy administration mount. Registered targets are `users.PosUser` (`users/admin.py:20`), `stores.Store` (`stores/admin.py:6`) and inherited `auth.Group`. `registerAdministrationHistory(app, config, db, options?, warehouse?, clock?)` and `readAdministrationHistoryOptions(env?)` are exported from `src/modules/administration-history/index.ts`. The frontend export is `AdministrationHistoryPage({user})` from `frontend/src/pages/administration/history`; its route is `/administration/model-history`, with optional router state `{model:'operator'|'store'|'group',objectId}`. No new migration or worker is required.

`GET /api/v1/admin/model-history/capabilities` reports currently permitted models. `POST /api/v1/admin/model-history/search` accepts only `model`, `objectId`, `from`, `to`, `page`. Filters stay out of URLs. Objects must exist on the writer; archived stores remain valid objects. An imported group resolves through its reconciled legacy ID, while a new rewrite group returns an explicit empty legacy-history notice. Rewrite receipts are not represented as Django logs. Current active internal role1 staff status and verified administration-access reconciliation are mandatory; each model requires its source view **or** change permission, or current superuser status. Authorization is checked again after reader I/O. These POS scope rules deliberately restrict the source admin site's broader staff policy.

Django4.2.5 `ModelAdmin.history_view` orders oldest first and uses a fixed100-row paginator. Malformed page values select the first page; negative/zero/out-of-range values select the last page, including one empty page for no results. Exact decimal object IDs remain strings. Raw current actor usernames and Python-stripped full names match the history template. Structured change messages reproduce `LogEntry.get_change_message()` under the source en-us locale. Naive DATETIME wall values and microseconds remain intact; displayed labels reproduce source `DATETIME_FORMAT` without browser-zone conversion. Source `USE_TZ=False` is verified; deployed `TIME_ZONE` is not, so `BUSINESS_TIMEZONE` must be accepted against production before date routing is certified. An explicit primary-key tie breaker makes equal timestamps deterministic; source ordering for timestamp ties is unspecified. Structurally corrupt JSON messages display a static unavailable marker instead of reproducing a framework exception. Input size limits and a4MiB message bound fail closed on unsupported data.

The exact current business day uses only the data reader, with a repeatable-read, read-only transaction, one metadata check, one count and at most100 joined rows. No-date/all-history, mixed, older and future ranges use BigQuery exclusively. There is no historical MySQL fallback. The SQL projection joins current actor names rather than querying once per row; Django's original history also uses `select_related`, so no source N+1 improvement is claimed.

Deployment options are strict and disabled when unset:

```dotenv
POS_ADMINISTRATION_HISTORY_MYSQL_CONTRACT=django-admin-log-en-us-v1
POS_ADMINISTRATION_HISTORY_MYSQL_ACTOR=auth-user
BQ_ADMINISTRATION_HISTORY_VIEW=reviewed-project.dataset.admin_history
BQ_ADMINISTRATION_HISTORY_MATCH_UDF=reviewed-project.dataset.admin_history_match
BQ_ADMINISTRATION_HISTORY_CONTRACT=django-admin-log-en-us-v1
```

These values are acceptance declarations, not evidence that a source is correct. `mysql-admin-shipping-schema.json` verifies the supplied reader's8-column `django_admin_log`, including `DATETIME(6)`, signed INT IDs, unsigned SMALLINT action flags and latin1_swedish_ci text. Its actor FK points to `auth_user`, **not** the pinned source's configured `PosUser`. `mysql-auth-history-schema.json` verifies that actor projection; no production rows were read. Runtime checks require exactly one same-schema `user_id→selected_actor.id` FK before daily history is read. Configuring `pos-user` against the supplied auth-user FK fails closed, even if numeric IDs overlap. Supporting another operational source still requires accepting its physical column contract and actor binding; the environment flag cannot verify provenance. Current permissions/object scope always come from the rewrite's actual `PosUser` writer, independently of the historical actor dimension. The current operational POS history source remains unaccepted.

The BigQuery publication must expose the complete accepted source log population, with `id` STRING, `action_time` DATETIME, exact fixed-microsecond `action_time_mysql` STRING, `actor_id` STRING, current `actor_username`/`actor_first_name`/`actor_last_name`, `action_flag` INT64, `change_message` STRING, `app_label`, `model`, `object_id`. Actor names must come from the accepted log actor source at read time; joins must not duplicate or drop logs. Orphaned actor data fails validation instead of inventing an actor. The required scalar UDF has signature `(left STRING,right STRING,operation STRING) RETURNS BOOL`, supporting `app_label.exact`, `model.exact`, `object_id.exact` with the accepted MySQL column collations and padding semantics. A generic Unicode case fold is not an accepted latin1_swedish_ci substitute. In particular, source object text comparison preserves the distinction between `01` and `1` while matching appropriate trailing spaces. The single bound query returns count/page/ordered-array together, validates envelope count/order/types and never interpolates requested object IDs. The adapter/reducer/UI are executable; the real view/UDF publication and source equivalence are still release gates. No live BigQuery parity is claimed.

Fourteen focused backend tests include9 native isolated MySQL workflows. Native source queries execute actual Django `LogEntry`/`Paginator`/message methods against synthetic local tables, using an explicit synthetic actor model to represent the selected physical binding. The pure oracle covers29 message/name vectors,108 paginator combinations and12 source date labels. Tests cover exact object IDs above2^53, native text padding, archived objects, imported/new groups, source binding mismatch, current grants/revocation, no-fallback routing, malformed warehouse envelopes and strict HTTP/cache behavior. Four Chromium workflows cover paging/filter bodies, HTML escaping, group selection/readiness retry, offline privacy and stale actor dispatch. These are component tests, not full deployed administration workflow certification.
