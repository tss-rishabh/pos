Conditional location-settings fix:

```sql
CREATE INDEX ix_tss_settings_platform_id ON tss_settings(platform, id);
```

Equivalent response-preserving query shape:

```sql
SELECT id, value
FROM tss_settings
WHERE platform = ?
ORDER BY id ASC
FOR UPDATE;
```

The API applies the source code normalization/sorting rules after locking rows and writes the same serialized list with bound ORM values. This index changes access and locking scope, not ordering or returned values. Concurrent local MySQL tests verify that both additions survive and a repeated normalized code returns a conflict.

Do not create a new covering price-list index merely to speed up `first()`: the source ordering specifies product ID while multiple location rows can share it. Changing the chosen index can expose ambiguous tie behavior. Confirm the deployed schema and expected location precedence before such a change.
