# Offline cash completion and reconciliation

This is a new user requirement, distinct from saving a cart offline. The selected stock policy is **cached stock with manager reconciliation after reconnecting**. A completed receipt records collected cash even when stock, authorization or import conflicts exist. It is never downgraded to a draft, repriced, voided or deleted to resolve a conflict.

## Implemented lifecycle

1. While connected and checked in, the operator registers an Ed25519 device key. The private browser key is nonextractable and survives IndexedDB reopen. The server returns a signed, bounded store/counter/operator/device authorization and an exact source price table for every allowed quantity. The default maximum is20 units per SKU; configuration can allow1–99. The grant expires within8 hours and before the signed business day ends. One active grant per device is reused across issuance retries, retaining its receipt sequence and cash budget. Identity changes revoke the old grant; its collected receipts remain recognizable.
2. Counter cash completion verifies the signed source prices, current cached operator/store access, session expiry and logout tombstone inside the durable IndexedDB transaction. It signs the immutable receipt, consumes its sequence/budget, creates sync work and retires only the original reviewed snapshot. Concurrently edited quantities survive under a new draft UUID. Paid online completion and nonfinancial clear markers remain separate.
3. The 80mm receipt can print and reprint without a connection, including after reload. It uses saved item/tax/cash/change values. Its identity, body and money do not change after import. It is a cash receipt; the authoritative tax invoice is a separate online document. The same sandboxed native print-dialog path is used in web, Windows and macOS builds. Chromium printing/layout is tested; Windows/macOS physical printer and signed installation certification remains a release gate.
4. Reconnect uploads the **same signed receipt**, with claim fencing and idempotent server acceptance. Receipt/line/grant-consumption/event/close-impact writes commit together. A revoked grant, changed identity, bad clock or shortage keeps the collected cash and becomes a manager conflict. Replaying acceptance does not consume another sequence or stale a subsequently reclosed day.
5. A clean accepted receipt belonging to the current cashier gets one automatic order-import dispatch. IndexedDB first commits an opaque operation ID, original expected version, actor and fenced attempt. Simultaneous tabs cannot dispatch independent intents. A saved dispatched/unknown intent is never automatically retried. Later background work only reads its outcome; the original cashier can explicitly retry the exact saved intent after a fresh GET. A manager handoff never silently imports another cashier's receipt. Conflicts remain manager-only.
6. GET-only status refresh verifies the original signed envelope, exact cash/scope fields, monotonic version and immutable imported order link. A confirmed import stops local pending-stock subtraction; the receipt, key, import intent and sync evidence remain. Cached role/user type/full store assignments are rechecked before both claim and publication. Logout/account switches stop work without deleting money.
7. A checked-in manager can acknowledge a conflict, approve the exact receipt/version or request an import. These are separate actions. Approval records immutable receipt hash, authorization ID, reviewed conflicts, reason and timestamp attribution. Staff cannot approve; the same currently authorized manager must execute an approved import. A valid original timestamp cannot be changed. Invalid device time needs an unambiguous wall-clock time inside the signed business day/window; original device time and cash remain intact.
8. Import obtains a **read-only source constructor template**, then uses one writer transaction for the order, source HP/refund/cancellation/audit rows, cash settlement, tax-invoice sequence, conditional inventory projection, durable synchronization work, native checkout hashes, signed immutable import proof, receipt→order link and imported receipt version. No payment confirmation or source `PosOrder` dispatch occurs. HTTP work happens before the transaction and cannot create an order. An interrupted response is recovered by writer proof; it never creates another order.

The original cashier remains bound in the receipt, source order/cashier fields and sealed proof. Import events, inventory mutation audits and delivery request/user correlation identify the actual authorized importer. Historical signing keys are append-only; existing keys need no shared global UPDATE during another sale.

The private providers are concrete pinned compatibility code under `compatibility/upstream/offline-cash-pricing`. They execute original hydration, price guard, calculation, constructor and refund methods without persisting carts or orders. Source API commit is `2960acbea10c4eaf16b6d99e15ff6e03ef7724c5`. Dynamic GST/slab/location settings and per-quantity values are frozen; no Node/browser tax formula replaces them. Eligible/excluded SKU IDs must be a unique disjoint exact partition of the request. Gift issuance, screening caps and other unsupported coupled product operations are explicitly excluded; corruption or SQL ambiguity fails the entire snapshot.

Private calls use JSON bodies, no redirects, bounded streaming responses, request/operator correlation and secret headers. Raw provider bodies, personal data, cookies, tokens, OTPs, SQL errors and keys must not appear in logs.

## Strict schema and source anomalies

The actual source constructor emits empty unset `orders.ship_date` and `ret_ex_request_date`, but verified legacy columns are nonnullable DATETIME with no defaults. Default strict MySQL rejects those values. The concrete review candidate is `compatibility/upstream/offline-cash-import/001_unset_event_dates.sql`; it makes only those unset event timestamps nullable, does not rewrite old rows and is **not** auto-registered or applied. Import verifies the real writer columns before proceeding. No code changes `sql_mode` or invents shipment/return dates. See the adjacent `improve-query.md` for exact mapping and legacy-consumer review requirements.

The owned generated import ORM maps every verified physical order/HP/store column. It preserves source numeric strings until MySQL binds/stores them, including FLOAT/DOUBLE and native DECIMAL remainder behavior. Native post-storage invariants recheck the frozen source totals. `LAST_INSERT_ID()` is cast to a decimal string on the transaction connection; no unsafe JS numeric order ID is used. The MOBILE reference generator has48 deterministic comparisons against the literal original method, including BIGINT IDs.

The literal source refund helper can overwrite all same-SKU HP rows with the final per-product amount while its audit rows retain distinct per-HP allocations. The user explicitly approved the per-HP correction. The private template executes pinned original code with the reviewed two-line SQL patch `patches/refund-by-hp-id.patch`, and both template and immutable seal require `refundAllocationContract=pos-refund-per-hp-v1` plus patch SHA256 `e156c0c281cf5d846b6ae88cd7824959babe2069ed409ca9dff31b7882945f11`. Negative/non-cent/unsafe totals or per-HP/audit mismatch still fail. The original unpatched behavior remains in independent source oracle evidence; corrected behavior is identified as an approved divergence. Auxiliary flags4/13 and primary19 come from the original `get_flags` method/current category metadata.

Ordinary online POS creation/confirmation/payment also requires the approved refund contract/hash and actual native per-HP/latest-audit correspondence. It cannot be enabled safely with a flag against bad allocation rows. Validation after order creation retains its checkpoint before confirmation; a mismatch cannot recreate that order or dispatch confirmation. Charge/settlement rechecks freeze a changed allocation without dispatching the same charge again. The production API-v2 patch has not been applied by this work.

## Accounting and recovery

The signed server business date determines attribution. Device completion time is not trusted to move cash to another day. First server acceptance locks current check-in/operator before Store, preserves frozen close amounts and appends a receipt→close impact; it stales only the latest affected close version once. Import uses the same Store lock and does not itself stale a close or add cash a second time.

Finance includes every accepted/conflicted/importing/imported receipt payable once, independent of source order status. It excludes an ordinary imported cash order only after verifying a trusted Ed25519 seal, exact receipt/link/date/store/counter/money/customer and structural order/HP proof. Later audited returns/status/price changes retain original collected cash; refunds/cash-outs remain separate outflows. Missing/tampered proof stops reconciliation rather than silently losing or doubling cash. No endpoint voids a collected-cash receipt or invents a cash-out.

Unknown local acceptance is safe to replay because it only writes the immutable receipt. Unknown import outcome requires a writer GET/read of the sealed link. Automatic import stops after its first durable dispatch, including after reload or a tab crash. An explicit retry first reconciles with GET, then retains the exact operation ID/version and current original-owner binding; changed versions or conflicts require manager review. The local claim has a30-second in-flight grace, but expiry alone never authorizes an automatic retry. Import metadata contains only opaque references/static error codes, survives logout, and does not alter collected cash. No external order/payment side effect is retried. Approval and acknowledgment uncertainty can be reconciled using the returned audit operation refs and exact receipt versions. A new operation ID is not permission to replace a previous cash receipt or order.

Server receipt acceptance and import recheck expired authorizations even when device completion time claims an earlier valid instant. Late cash is retained as a manager conflict. Normal payment endpoints reject any imported offline receipt/link before collecting another payment, independent of later mutable order/payment statuses.
