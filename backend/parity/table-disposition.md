Rules applied:
- (a) covers deleted features: screening, `backend/compatibility/**` including the customer-contacts service, cash-return intents, demo mode, CSV
  import authority succession, and offline-cash IndexedDB/import-proof. It also covers rewrite-only bookkeeping: outboxes, proofs and hashes,
  projection confirmations, and performance capture. Where a DELETE table also drove a real legacy side effect, the notes say how that
  side effect now happens: synchronously, as legacy does, or as a Redis queue job that mirrors a named Celery task or thread.
- (b) is used only where legacy persists the same fact. The row names the table, the columns and the legacy file:line.
- (c) covers ephemeral state: sessions, OTP and challenges, idempotency windows, locks and leases, rate limits, recovery claims, and job queues.
  The row gives the key pattern, value, TTL and the legacy precedent. Legacy key names are reused wherever the rewrite serves the same flow.
- (d) is used only for legacy-reachable behavior whose durable state has no existing table and is unsafe in Redis. **These rows stop
  Phase C until the user decides.**

## Proposed Redis conventions (Phase C)

- Legacy keys are reused verbatim where the flow is the same legacy flow: `login_otp:*`, `check_in_{uid}`, `check_in_list_{store}`,
  `auth_qr_{uid}`, `mpos_download_qr_{uid}`, `{uid}_{store}_{counter}_{tab}` PG-discount OTP, `{store}_{tab}[_{prod}]` salesperson,
  and `gift_card_{tab}_{gv}`. Keys that exist only in the rewrite use the `pos:` prefix.
- Idempotency receipts: `pos:idem:{scope}:{actorId}:{key}` → JSON `{requestHash, status, result, requestId}`, `SET NX`. The TTL is per row,
  normally 24 h. A mismatched `requestHash` keeps `IDEMPOTENCY_CONFLICT`.
- Locks: `SET NX EX`, with a token checked on release. Legacy precedent: `order/tasks.py:152` HL reject lock.
- Job queue: a single Redis-backed queue (BullMQ on the existing redis dependency) with the queue names legacy Celery routes use:
  `core`, `store`, `report_queue`, `order` (`POSAdmin/settings.py:418-431`). This replaces every outbox table and the 15 `worker:*` scripts.
- Redis must not be configured to evict these keys (`maxmemory-policy noeviction`, or a dedicated logical DB). Legacy kept OTP and
  check-in state in the same Redis (`POSAdmin/redis.py`).
- Keys reused from legacy only interoperate with a running legacy app if both use the same Redis host and DB
  (`REDIS_HOST`/`REDIS_PORT`, db=0).

## Decisions surfaced that are not (d) rows (user/primary-agent sign-off)

No table qualified for (d). The rewrite-only or legacy-dormant behaviors below still lose something when their tables are deleted:

1. **Google SSO subject binding** (`pos_rewrite_operator_google_identities` → DELETE). Legacy has no Google SSO: `POSAdmin/settings.py:90`
   lists only ModelBackend and EmailBackend. spec.md asks for a stable OIDC subject binding. Without a table, SSO can only match the
   verified email to `pos_user.email`, so email reassignment is no longer detected.
2. **Gift-card batch archive password** (`pos_rewrite_gift_card_batch_jobs` → DELETE). Legacy generates the batch synchronously
   (`core/views.py:2195-2203`) with a derived zip password: the user's phone digits plus the collection number (`helpers/helpers.py:1345-1350`).
   The rewrite's random password, which can be fetched again later, has no durable home. Either return to the legacy password or
   show the password once.
3. **CSV order punch-in is dormant in legacy.** The upload views and URLs are commented out (`core/urls.py:72-76`, `core/views.py:978-1093`).
   Only the Celery tasks remain (`core/tasks.py:50-62`). The kept "pause inconsistent CSV tenders" workflow is mapped onto
   `pos_csv_upload.failed_data`. If product confirms punch-in stays dormant, the whole order-import family can become DELETE.
4. **Payment-correction cash ledger** (`pos_rewrite_payment_correction_cash` → DELETE). Daily sales and cash reports go back to
   legacy behavior: a reversal zeroes the original order's tender, and the close buckets by `orders.created_at`
   (`order/views.py:710`, `report/day_close_services.py:323-326`).
5. **Return customer OTP** (`pos_rewrite_return_verifications` → REDIS). Legacy returns require only check-in
   (`order/views.py:885-914`). The table is kept as an ephemeral Redis proof only because recovery claims carry a verification ID.
   Under strict parity it is DELETE.

## Schema conflicts found outside the `pos_rewrite_*` tables (need user/primary-agent decision)

1. **Offline billing limits cannot use `tss_settings.platform` as planned.** In production `tss_settings.platform` is an
   **ENUM** of 76 fixed values. It does not contain `POS_OFFLINE_BILLING_MAX_MINUTES` or `POS_OFFLINE_BILLING_MAX_ORDERS`, so
   inserting those rows needs `ALTER TABLE`, which the freeze forbids. Legacy declares `platform` as a CharField
   (`stores/models.py:9`, `managed=False`), but the physical column is the enum. The other options are: key the rows by `name`
   with `platform` NULL, which breaks the legacy `filter(platform=…)` pattern from `core/views.py:1949,1953`; use env/config; or approve
   the ALTER. **Ask the user.**
2. **`orders.order_ref_no` is never written by legacy POS.** At 78d5b63 the POS only reads it (`order/views.py:2765,3295,4204`).
   API-v2 writes it. It is also the source of the payment `transaction_id` (`helpers/helpers.py:713-736`) and feeds the Glassbox
   finance export (`report/glassbox_finance_feed_queries.py:135`). The offline-sync design needs API-v2 `pos/order` to accept the
   provisional reference, or needs a new POS-side `UPDATE orders SET order_ref_no` after creation. Confirm before W6 builds sync.
3. **The `sql_mode`-dependent legacy writes cannot be reproduced without knowing production `@@GLOBAL.sql_mode`.** Legacy writes
   `gift_voucher_history.platform='GV_ADD'` (`core/views.py:1543-1546`) and `has_products.type='FREEBIE'` into enums that lack
   those values. Capture `sql_mode` read-only and add it to the snapshot.
4. **Snapshot gaps.** Mappings below rely on legacy tables that are not in the 114-table snapshot: `django_session`,
   `auth_group`, `auth_group_permissions`, `auth_permission`, `pos_user_groups`, `pos_user_user_permissions`, `django_content_type`
   (present) and others named per row. Capture their DDL read-only (`SHOW CREATE TABLE`) before Phase C.
