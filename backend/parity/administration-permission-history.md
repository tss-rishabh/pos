# Read-only SpecialPermission activity history

Source baseline is `backend-pos-web@78d5b63d6a149a6bf2c748fa1d191799c59ecb8a`: `core/views.py:1177 SpecialPermissionView`, `core/datatables/special_permition_datatable.py:12 special_permition_datatable_view` and `core/templates/special_permission/index.html`. The read-only page/data portion contributes two traced APIs; benefit/global mutations remain checkout-owned and are not certified here. No complete source route is certified.

`registerSpecialPermissionHistory(app,config,db,options?,warehouse?,clock?)` is exported by `src/modules/special-permission-history/index.ts`. It registers no-store GET `/api/v1/admin/special-permission-activity/capabilities` and POST `.../search`. Search/platform/date/page values remain in strict request bodies, with no contact-bearing GET alias. Parent authentication, expected-actor binding, CSRF, sanitized errors and request/user/module/resource event IDs apply. Current active internal roles1–3 are rechecked on the writer. The history is global: the physical source table has no store column, and a store assignment is not fabricated as a filter.

The six source data fields retain exact signed BIGINT ID strings, platform, nullable comment, naive datetime, raw `first_name + ' ' + last_name`, `unknown` for a missing operator and `NA` only for a null/empty recipient. Whitespace-only names/recipients are preserved. Operator lookup includes inactive rows. Source search replaces double quotes with single quotes, escapes literal percent/underscore/backslash and searches recipient/comment/platform/MySQL datetime only; operator names/IDs are excluded. Platform parsing preserves source comma/entity handling and Python whitespace behavior, including filtering empty entries before stripping. Sort controls are ignored in the source; the rewrite uses explicit ascending numeric-ID order rather than relying on an un-ordered database plan. Negative, non-aligned and out-of-range offsets return the first page. Both returned totals equal the filtered count.

Only an exact current business-day range uses the data reader. A repeatable-read, read-only transaction performs one count and one bounded LEFT JOIN page, replacing full-result materialization and per-row operator queries. The date predicate uses half-open DATETIME bounds rather than `DATE(created_at)`, retaining inclusive source days without a timezone conversion. `BUSINESS_TIMEZONE` must match the deployed source setting, which is not yet verified. Saved physical metadata preserves the platform/comment/recipient `latin1_swedish_ci` comparisons; no guessed Unicode folding is introduced. Source and rewrite reject an incompatible mixed-character-set comparison; the API returns only a static error, with no SQL/parameters/request text.

No date, any previous/future date and mixed-day requests use BigQuery exclusively. `BQ_SPECIAL_PERMISSION_ACTIVITY_VIEW` and `BQ_SPECIAL_PERMISSION_ACTIVITY_MATCH_UDF` are validated fully qualified deployment resources. The shared warehouse client enforces billing/runtime/row guards. One bound query returns count plus at most500 rows from one snapshot; the reducer verifies exact counts, page coverage, ascending distinct lossless IDs and raw-name projection. Missing mappings or a required source-comparison routine fail closed without a historical MySQL fallback. `administration-permission-history-contract.json` specifies the actual view fields, per-field UDF signature, source comparison semantics, freshness/integrity and deployment acceptance requirements. Ordinary Unicode LOWER/accent removal is not a valid substitute for the physical Swedish collation. No routine/view was deployed or live BigQuery SQL executed.

Offline cached rows remain readable while network filtering/paging is disabled; this audit has no write actions.
