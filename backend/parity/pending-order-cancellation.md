# Pending cash-on-counter whole-order cancellation

Source `backend-pos-web@78d5b63d6a149a6bf2c748fa1d191799c59ecb8a` shows **Cancel Order** only for method14, Pending payment and Order Placed (`order/templates/order/show.html:65`). Its `AjaxOrderCancelView` (`order/views.py:2900`) calls API-v2 `CancelPosorder` (`controllers/OrderController.py:11478`, `2960acbea10c4eaf16b6d99e15ff6e03ef7724c5`), then changes order/payment to4/2, changes exact lines, logs an empty counter transaction and increments existing store stock. It does not refund unreceived counter `pay_amt` or call a PSP refund.

The original flow has staged wallet commits, a middleware commit that ignores request success, no command idempotency and a separate swallowed-error/implicit-commit stock routine. The literal read-only oracle `tools/checkout/pending_cancellation_oracle.py` executes both original handlers against inert synthetic adapters. Six cases prove duplicate-SKU/long-ID behavior, no cash refund, partial source effects on a later error and source success despite a missing stock association. The new atomic failure/refusal behavior is an explicit correctness correction, not a claim that those unsafe branches match source success.

## Implemented transaction boundary

`registerPendingOrderCancellations` is called by `registerCheckout`. Three traced resources are registered at `/api/v1/stores/:storeId/orders/:orderId/cancellations`: GET context, POST `{operationId,snapshotHash}`, and GET `/:cancellationId` for original receipt recovery. The source arbitrary paid/revert API is not used.

Creation requires:

- Exact pending method14 order, every HP PLACED, one receiving store/counter and ordinary native header/line/consent/refund/gift proof.
- Current operator/store/organization access and exact current check-in; check-in/current actor→Store→order lock order matches finance. DB-only deadlocks may retry; no external HTTP occurs inside this transaction.
- No recorded tender/manual-paid cash, immutable offline cash, unresolved/paid attempt or unaccounted legacy provider evidence. Failed/cancelled split cash still requires review; it is not silently returned or discarded.
- Exact unrefunded per-HP audit correspondence. Cashback spending remains unsupported. With no restoration profile, benefits and configured membership SKUs remain refused; the approved, separately gated profile below supports proved Money/Points/voucher/membership restoration.
- Explicit `POS_PENDING_CANCELLATION_CONTRACT=pos-pending-order-cancellation-v1` and a reviewed `POS_PENDING_CANCELLATION_MEMBERSHIP_PRODUCT_IDS` JSON ID array matching API-v2's dynamic EXCLUSIVE_PRODUCT/EXCLUSIVE_UPGRADE_PRODUCT settings. Absence is not interpreted as an empty list.
- Configured transaction-scoped `StockProcedure`; the old implicit-commit CALL is never selected by this module.

Duplicate SKU quantities are grouped and restored once. Sorted Product→aggregate→ProductStore locks, unique existing associations, integer bounds and a post-projection stock check protect the mutation. Availability/deletion flags and sibling associations are preserved, matching pending-cancellation scope rather than return-restoration behavior. The stock/audit/status changes, `cashback_refunded`/refund flags, empty-cash transaction log, `order-cancel` synchronization event and HMAC-bound immutable cancellation receipt commit together. Latest-close impacts are retained in the receipt; only the latest CLOSED/STALE snapshot is marked stale, preserving its frozen totals and all older versions.

Apply the additive `cancellations/migration.sql` through the shared deterministic runner. It creates only `pos_rewrite_pending_order_cancellations`, unique by order/command, with original operator and request ID up to128 bytes. Confirmed receipt reads/replays verify immutable bindings even when configuration or mutable order state changes. Another payment is refused from the immutable cancellation independently of current source status columns.

The Orders page exposes explicit review/confirmation. A local ID/snapshot-only intent is saved before POST; reload/unknown outcomes use GET only, and an absent receipt permits only an explicit exact retry. Cancellation never clears a local cart, creates a paid receipt or claims a cash refund.

## Approved benefit restoration

The user explicitly approved preserving **each original earning expiry**, leaving expired value unusable, consuming/auditing only the exact remaining allocated portion once. The already approved Money correction leaves Cashback untouched and writes the Money ledger rather than the unrelated reward ledger. The source anomaly/differential remains in [decision.md](../compatibility/upstream/pending-cancellation/decision.md); these corrections are not source-success parity claims.

`benefits.ts` rechecks the current exact native header, customer identity/eligibility and every HP/audit amount before taking original earning mappings/history under locks. Physical allocation and history types/defaults come from `evidence/mysql-pending-cancellation-benefits-schema.json`: allocation amounts are DOUBLE, and NULL returned amounts are ambiguous rather than zero. Missing/orphan/foreign/incomplete allocations fail before a write. Mappings are sorted by exact IDs, including IDs above2^53; source Python/text-protocol FLOAT boundaries are retained. Different original expiry and bonus buckets remain separate. Expired consumed portions receive their exact negative audit and original expiry, without spendable balance or a new validity window. All returned maps, Money/Points histories, native balances, stock, source flags/statuses, day-close impact, synchronization and the immutable receipt share one transaction. Only that transaction can consume its private single-use plan.

Voucher restoration requires exact original order/customer/voucher ORDER_PLACED debit, matching per-HP/header total and coherent debit before/after values. A verified visible `(order_id,gv_id,id)` ledger index prevents unrelated FOR UPDATE scan locks; the source additive candidate and exact-result local EXPLAIN check are in root `improve-query.md`. Customer→collection→voucher locks retain the current collection block, voucher disabled state and validity. GIFT_CARD also needs matching existing0015 issuance/native hash; missing/changed legacy funding is reconciliation, never a fabricated backfill. The writer credits the exact original debit and appends ORDER_CANCELLED history. It never reactivates arbitrary status0; unavailable retained credit is explicit in context/receipt/UI. Ordinary GIFT_VOUCHER keeps source date semantics.

Membership needs the reviewed source product IDs, a purpose-keyed native before/confirmed EAV proof and monotonic customer revision. The executable source-pinned producer now surrounds the real API-v2 `PosOrder` block/all eight `userDal` writers and the Go activation boundary. The same true before-state survives staging and activation. Reviewed native INSERT/UPDATE/DELETE/email triggers fence changes from other writers, with exact body/index/collation checks and no automatic source DDL. The cancellation consumer compares exact current hashes/revision/order/customer/header and restores only the proved before-state, preserving prior entitlement and expiry. Changed ownership, duplicate native-collation email, missing/changed fence, malformed/missing proof or absent fresh-reader contract is refused. UTC native timestamp hashes preserve instants across SQL time zones. Details, deployment sequence and actual Python→Go→Node native evidence are in [membership-producers.md](../compatibility/upstream/pending-cancellation/membership-producers.md). The source patches/triggers remain unapplied; historical backfill is not fabricated.

Activation requires explicit `POS_PENDING_CANCELLATION_BENEFIT_POLICY=pos-cancellation-original-expiry-v1`, `GLOBAL_BENEFIT_WALLET_LOCK_CONTRACT=pos-wallet-user-lock-v1` and `POS_PENDING_CANCELLATION_VOUCHER_LOCK_CONTRACT=pos-voucher-user-lock-v1`. Defaults stay blank until the independent shared writers are certified. Membership additionally requires `POS_PENDING_CANCELLATION_MEMBERSHIP_WRITER_CONTRACT=pos-cancellation-membership-provenance-v2`, `POS_PENDING_CANCELLATION_MEMBERSHIP_CACHE_CONTRACT=pos-membership-fresh-reader-v1` and `UPSTREAM_POS_MEMBERSHIP_CONTEXT_CONTRACT=pos-membership-fresh-reader-v1` (Node checks source response marker/exact revision), plus a separate32-character-or-longer `POS_PENDING_CANCELLATION_MEMBERSHIP_PROOF_KEY`. Apply `cancellations/benefit-migration.sql`, then `cancellations/membership-producer-migration.sql` using the shared runner. The nullable additive digest does not turn old/v1 records into evidence. Separately reviewed source triggers and producer configuration are detailed in the linked runbook and are excluded from automatic migrations.
