# Model administration groups and permissions

`users/admin.py` replaces the personal-info fieldset of Django4.2.5 `UserAdmin`; its inherited permission fields and default `GroupAdmin` remain present. The framework combines direct and group grants, active superusers satisfy model permissions, and the administration site requires an active staff account. The rewrite's pure evaluators match32 native framework cases generated in an isolated in-memory SQLite database. See the pinned [Django UserAdmin/GroupAdmin](https://github.com/django/django/blob/4.2.5/django/contrib/auth/admin.py), [permission models](https://github.com/django/django/blob/4.2.5/django/contrib/auth/models.py) and [ModelBackend](https://github.com/django/django/blob/4.2.5/django/contrib/auth/backends.py).

Eleven concrete traced APIs implement capability reporting, permission catalog/search, group list/detail/create/edit/delete and operator staff/superuser/group/direct-grant reads/updates. Source grants live in rewrite-owned tables with indexed compound keys and stable `app_label.codename` identities. Cursor reads use the primary reader after writer-current authorization; mutations, optimistic revisions and idempotency receipts use the writer. Group membership and permission changes increment a BIGINT revision, so operator editors detect changed effective group grants. All responses prohibit shared caching. Receipts retain actor/request/resource IDs, hashes and static results; they contain no staff contact data or submitted body.

POS role/store rules remain part of authorization. Model administration is restricted to current internal role1 staff accounts. Read access evaluates source model grants on the writer. Global privilege mutation additionally requires an existing active staff superuser; another superuser must change your own flags/grants. This intentionally hardens source delegation behavior. Group removal atomically removes its memberships and grants. Sensitive flags, groups and direct-grant changes permanently revoke affected authentication through the shared writer-transaction auth epoch. Group changes lock members in numeric-ID order and invalidate in bounded batches of500; a501-member SQL case crosses that boundary. Restoring earlier flags/grants cannot revive previous sessions or login proofs. Actor-bound pending MFA enrollments are also cancelled. No-op group saves preserve authentication.

The React Model access page implements group CRUD/search and a permission picker that preserves selections when search/pagination hides rows. The operator access dialog changes flags, group memberships and direct keys in one transaction and preserves unloaded selections. Writes require connectivity. Chromium workflows use isolated API fixtures and exercise group lifecycle plus operator updates; no production access changes occurred.

Apply `src/modules/administration/access-migration.sql` after the other administration migrations. It creates only rewrite catalog/groups/grants/reconciliation/receipt state and a registry row. **It does not create the missing legacy Django auth tables.** Read-only evidence currently exposes `tss.auth_permission` and `django_content_type`, but not this application's group/M2M tables; the visible `mobile_cms` tables belong to another application. The operational auth writer and all four joins must be verified before accepting production parity.

`tools/administration/reconcile-access.ts snapshot.json` previews a validated snapshot without constructing DB/storage clients. Applying requires `--apply snapshot.json`, `ADMIN_ACCESS_SOURCE_VERIFIED=true`, `ADMIN_ACCESS_IMPORT_OPERATOR_ID` and the explicit writer service configuration. The selected operator must currently be an active internal role1 staff superuser. The snapshot must contain every writer operator and exactly matching staff/superuser flags, all permission identities, groups and joins; unresolved IDs, duplicate/ambiguous keys or inconsistent flags fail. It refuses nonempty rewrite access state, imports in bounded batches in one transaction and records the proof fingerprint, hash, counts, actor/request IDs. The exact same snapshot is replayable; another source snapshot requires a reviewed migration. No legacy group schema or `mobile_cms` grant fallback is inferred.

Snapshot shape (IDs are strings):

```json
{
  "version": 1,
  "sourceVerified": true,
  "sourceFingerprint": "<64-hex hash of reviewed source identity/schema/export evidence>",
  "exportedAt": "2026-11-16T00:00:00Z",
  "permissions": [{"key":"stores.change_store","appLabel":"stores","model":"store","codename":"change_store","name":"Can change store"}],
  "groups": [{"legacyId":"10","name":"Store controllers","permissionKeys":["stores.change_store"]}],
  "operators": [{"id":"1","isStaff":true,"isSuperuser":true,"legacyGroupIds":["10"],"permissionKeys":[]}]
}
```

The source proof flag/fingerprint attest reviewed provenance; they cannot replace validating the operational export. Duplicate `app_label.codename` keys across distinct model permissions require an explicit mapping decision and are rejected rather than silently collapsed. Import is a deployment operation requiring a complete maintenance snapshot, not a public HTTP endpoint. The current configured live snapshot remains unavailable, so the feature fails closed with `ADMIN_ACCESS_RECONCILIATION_REQUIRED` until reconciliation.

Regenerate framework evidence with `uv run --no-project --with django==4.2.5 python tools/administration/build_access_oracle.py`. It pins framework source hashes, runs native direct/group/superuser/site rules over32 combinations and never loads production Django settings or contacts MySQL. Tests also cover atomic import/replay/mismatch rollback, revocation, privilege escalation rejection, concurrent group uniqueness, stale group revisions, deleted/unknown grants, exact session invalidation and receipt replay against isolated local MySQL. These checks do not certify the entire deployed Django admin workflow.

Selected GroupAdmin deletion now has a body-only preview and an atomic selected-group command. POST `/api/v1/admin/access/group-deletion-previews` accepts `{groupIds}`; POST `/api/v1/admin/access/group-deletions` accepts `{operationId,groups:[{id,expectedVersion}]}`. Both are traced, private/no-store, writer-current, reconciled internal-superuser operations. The batch is bounded to100 groups,20000 permission assignments and100000 memberships; it retains operator accounts/financial identities, removes only reconciled rewrite group/M2M rows, deduplicates current actor locks and revokes authentication once per affected operator. Group versions already advance when operator memberships change, so a stale preview fails without partial deletion. One transaction covers all changes, permanent auth epochs and a request/actor-bound idempotent receipt. Identical-operation retry is safe even after a committed response is lost. This explicitly corrects the source bulk action's false deletion audit on transactional failure; it is not a response-identical query optimization.

The UI retains selections across body-only filters and lists every selected group in the confirmation. Four native SQL workflows cover replay/concurrency, stale membership/missing selections, failure rollback, current privilege/strict input checks and actor reauthentication. Three Chromium workflows cover hidden selections plus lost-response retry, refreshed stale confirmations and captured-actor dispatch. Source Collector/deletion permission behavior is pinned and executable in `tests/administration-history/collector.test.ts`; no live access changes or legacy auth-table deletes occurred.
