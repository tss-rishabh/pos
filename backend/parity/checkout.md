# Checkout, settlement and return verification

Source: `backend-pos-web` commit `78d5b63d6a149a6bf2c748fa1d191799c59ecb8a`. This document records bounded evidence, not production certification or complete legacy feature coverage. The repository-wide parity release gate must remain closed until the unresolved contracts and feature gaps below are addressed.

## Run the checks

Use the pinned Node 24 LTS version from the repository. From `backend`:

```sh
npm run typecheck
npm test -- tests/checkout
CHECKOUT_MYSQL_TEST_URL=mysql://root@127.0.0.1/pos_rewrite_checkout_test npm test -- tests/checkout/mysql.integration.test.ts
```

The MySQL suite refuses remote hosts and schemas other than the explicit localhost template. It creates a uniquely named temporary schema, constructs fixtures from the audited Drizzle mappings, applies checkout-owned migrations and drops the schema on completion. Provider calls are injected fixtures. It never charges a terminal, creates a live order, sends an email/SMS or writes to the supplied reader.

From `frontend`, build before the production-browser check:

```sh
npm run build
npx playwright test e2e/checkout/invoice.spec.ts
npx playwright test e2e/checkout/exchange.spec.ts e2e/checkout/discount-approval.spec.ts
npx playwright test e2e/checkout-recovery.spec.ts
npx playwright test e2e/checkout/gift-card.spec.ts
npx playwright test e2e/checkout/clearance.spec.ts
```

`tools/checkout/legacy_oracle.py` AST-extracts original Python methods without importing Django. Tests compare cart/benefit/order wire payloads, invoice-year and transaction-ID behavior, refund rounding/modes, Pine Labs and Paytm payloads, the warehouse inbound request, `pos/exchange` payload and 22 manager-approval threshold/fallback cases. Those payload comparisons do not establish full end-to-end response parity with the unavailable upstream services.

`tests/checkout/mysql.integration.test.ts` exercises actual transaction locks, simultaneous replay, version conflicts, lost-response checkpoints, provider-evidence settlement, cash split persistence, gift-card activation, day-close invalidation, return credit notes, hold inventory, cross-store authorization, line-specific extensions, exchange child completion/rejection retry/uncertainty, outbox claims and protected invoices. Gateway results are controlled fixtures; they do not certify the deployed providers or inventory routine.

The IndexedDB offline cash flow and the fast-cash checkout UI were deleted by W7 on 19 November 2026 (see [w7-report.md](w7-report.md)). Desktop offline billing replaces offline cash. [fast-cash.md](fast-cash.md) describes the removed fast-cash UI; only its backend settlement-note resource and source vectors remain.

The private invoice/purpose-only feedback correction, scoped log/privacy evidence and unapplied compatibility workers are documented in [invoice-security.md](invoice-security.md).

After the backend build, run `node dist/modules/checkout/worker.js` as a supervised worker, or append `--once` for one batch. It dispatches producer, engagement, return-email, exchange-email, manager approval and discount-used email events. It uses row claims with `SKIP LOCKED`, records delivery outcomes and freezes ambiguous/processing events for reconciliation. Supplying `Idempotency-Key` is additional correlation; no remote deduplication contract is assumed. Unknown external side effects are not retried automatically.

Financial events retain the enqueue request ID and operator ID. Individual delivery logs use that context, static module/resource/event identifiers and a unique event-instance ID. Batch summaries use the worker trace. Bodies, queries, credentials, customer contact details and raw provider/SQL exceptions are never logged.

## Financial safety and recovery

- Creating a session requires the persisted local draft UUID, snapshot timestamp and unique product/quantity manifest. The writer's unique operator/draft key makes simultaneous opens and lost-response retries return the same latest checkout. A changed store, counter, snapshot timestamp or manifest is rejected. Initialization is one leased `/draft-initializations` operation with each confirmed line checkpointed; known rejection resumes missing lines only, while an unknown outcome freezes. Quoting, submission and other mutations are blocked until the manifest is complete. An already completed import never overwrites later explicit cart edits.
- The browser retains the first review snapshot in owner-scoped IndexedDB across tabs/reloads, verifies the server draft identity/version/manifest before accepting any receipt, and never reloads original quantities into an initialized checkout. Paid completion archives the original snapshot atomically; newer local edits survive as a new sale UUID. The CounterPage production-browser regression covers closing, reloading, changing quantity and recovering a confirmed prepaid sale without another import/order. Server evidence is separately tested against isolated MySQL; browser payment results are fixtures.
- A terminal upload is pending, not paid. Settlement requires a confirmed status enquiry; Paytm success must match merchant, terminal, transaction and amount. A pending/uncertain attempt blocks another charge.
- Pine Labs cancellation is confirmed only by the provider's approved cancellation response. The original Paytm cancellation merely changed local flags; the rewrite fails closed until a real provider cancellation/void contract is supplied. Do not label that disabled path parity complete.
- An external order identity is checkpointed before confirmation. Uncertain order creation/confirmation is not repeated automatically.
- A successful confirmation HTTP response is checkpointed separately from invoice finalization. If local finalization rejects after that acknowledgment, `/order-finalizations` repairs only the local invoice/salesperson work and does not call order creation or confirmation again. An interrupted dispatched confirmation can use `/confirmation-reconciliations`: the existing order's writer proof must match before acknowledgement/finalization. It never calls order creation or upstream confirmation. A fenced 60-second lease permits restart after an interrupted recovery; stale workers cannot checkpoint, finish or clear its replacement lease. A fresh in-flight submission has the same 60-second grace. Success repairs the original submission receipt atomically. A never-dispatched or unknown order identity remains blocked.
- Ordinary submission and counter payment require the verified upstream projection contract before external order/charge work. Finalization and paid read/list/start replay/reconciliation verify the exact native header, receiving store/counter/customer and every has-product/SKU/quantity/price hash. Writer-paid status alone cannot complete the sale. Prepaid cached reads, mutation replays and operation receipts recheck proof; deletion/tampering cannot replay a previously cached paid receipt.
- PG/store discount approval follows the source store threshold policy and active manager fallback. Role-exempt and explicitly configured no-manager policies remain supported. Nonexempt operators can preview a discounted draft; order submission requires approval of the current server-calculated products, quantities, benefits, totals, remarks, customer, store and counter. The quote is refreshed before submission and changed terms require a new approval.
- Each manager code uses a keyed hash and a delivery-bound encrypted queue payload; no plaintext code is stored in the legacy audit. Codes expire, have five attempts per challenge and share a five-attempt/ten-minute operator budget and one-minute send cooldown across checkout sessions. Unknown email outcomes are frozen; request replay never resends. The source did not enforce these security controls.
- Discount audit fields are verified against `evidence/mysql-extra-schema.json`. The legacy `store_pg_disc_addons.pg_disc_otp` remains null, while approver/applicator IDs and names, remarks, store/counter and integer report amount are retained. Exact two-decimal amounts and approval IDs are retained in the rewrite audit. Combined remarks must fit the real 45-character legacy field; names use its 45-character storage bound. Applied notifications omit the raw code.
- Zero-total prepaid completion is a separate receipt source. It requires writer-verified payment status 4, delivered status 3, prepaid method 3, zero payable and matching store/counter/customer. Its receipt identity is the successful checkout submission operation, never a fabricated cash/terminal attempt. Replayed receipts recheck current paid state.
- Physical gift-card controls preserve individual card numbers and validity dates, default catalog denominations, and the source whole custom-value range of 1 through 10000. `DEFAULT_GC_EX_DAYS` defaults to the source 90 days; defaults use the business timezone. Adding cards requires the reviewed `UPSTREAM_POS_GIFT_CARD_CONTRACT=pos-gift-card-v2` compatibility contract. The pinned API-v2 currently ignores `gvprice`, uses colliding second-resolution IDs and rejects repeated cards of one product; the concrete patch and isolated source tests are in `compatibility/upstream/gift-card.md`. The rewrite verifies exact returned identity, price and face value, compensates a known custom mismatch, and freezes unknown additions/removals. A config flag does not bypass those checks. No patch has been deployed.
- Coupon, redeemed gift-voucher and wallet removal use the source payloads. Removing wallet benefits does not require renewed customer spending authority; adding a new money/points spend still requires the bound live customer verification.
- Order message preferences are held by the server. Confirmed order preparation stores the optional source NPS flag and a unique `order-sms` outbox row in the same transaction. The original `{order_id}` payload is retained, but the old `omnichannel-sms` target is now forbidden: source inspection found customer login-token issuance, raw parameter logs and provider credentials in URL queries. Rows stay pending without the new exact private contract/key. Delivery additionally requires a nonce/event/order/operator/request/body HMAC and the source `SMS Sent` acknowledgment; every unproved/unknown dispatched outcome freezes and never resends automatically. The private provider correction is still pending, so this gate must not be described as working SMS delivery. Browser labels say queued and do not imply payment or delivery confirmation.
- Returns allow original online/other-store purchases at an assigned, checked-in receiving store. Order-bound customer OTP proof is required; minimal return line data is exposed only after verification. Generic order detail remains scoped to its original assigned store.
- Customer lookup uses strict `POST /api/v1/stores/:storeId/customer-lookups` with `{query,counterId}`; the PII-bearing GET route was removed. Lookup requires the current check-in, returns minimal matching active customers, and avoids membership queries per result. Attachment and token prerequisites recheck the current account and block flag on the writer. Checkout, payment and reverse-flow clients bind captured operator IDs to API calls.
- Registration preserves source name/Indian mobile/optional email and birthdate/B2B or B2C/GSTIN fields and the `mobile@temp.id` convention. Its OTP is hashed and identity details/delivery code are encrypted with authenticated associated data. SMS and delayed WhatsApp fallback use the shared form POST transport, keeping contacts/codes/credentials out of URLs. A code has five attempts, shared phone/operator failure budgets and cooldowns; a resend invalidates old proof and cancels pending old fallback. The source self-verification bypass is intentionally rejected. Missing expiry/secret/provider configuration fails before queuing or account creation.
- Registration request identity and delivery queue commit together. An interrupted local request checkpoint can be repaired using the saved queue without another send; the same fenced lease prevents a stale worker from completing after reclamation. Account creation is checkpointed as dispatched before its external call. Unknown outcomes hold contact claims and cannot create another account; reconciliation requires one exact active writer customer matching the verified phone/email, and renewed phone proof after 15 minutes. Upstream tokens are discarded. The pinned upstream ignores registration GST/type fields; the rewrite persists those intended UI fields only through the bound writer identity. The registration code and pending fallback are consumed/cancelled after completion.
- Clear/detach confirms the customer cart and separate actor tab are empty, resets customer verification, discounts, gift metadata and salesperson assignments, and atomically persists terminal clear evidence with removal of owned customer/gift leases. The session cannot be reused or reimported. Clear evidence contains the original owner/store/counter/draft/version plus checkout/operation IDs, never a payment receipt. A later receipt-write interruption cannot downgrade the confirmed clear.
- The device binds the first validated checkout ID to its persisted review snapshot. IndexedDB V4 retires only that proved original snapshot and its queued saves, writes a nonfinancial clear marker and atomically creates a fresh empty draft or preserves later edits under a fresh UUID. Repeated/two-tab/reloaded callbacks reuse that result and cannot delete a newer draft. Snapshot review and queued saves reject cleared IDs. Optional recovery storage is removed only after the durable local transaction. Paid completion logic remains separate.
- Return acceptance, credit-note persistence, refund dispatch and local inventory completion are distinct durable phases. An uncertain warehouse/refund call freezes. `inbound-accepted` can continue an undispatched refund; `refund-confirmed` can repair local completion without another refund.
- Exchanges preserve the same-product replacement, salesperson, reason and size fields. A credit note at this operation's store/line/time proves the return leg. New acceptance requires the verified upstream contract setting. A confirmed rejection permits an explicit stored-pick retry only when no live/incomplete/orphan child exists; unknown child creation freezes. New cash collection is zero.
- Normal exchange completion requires writer-paid prepaid zero total, valid current child/line status, unrefunded line allocation and exact `pos-exchange-stock-v1` transactional stock proof. The rewrite never sets an unpaid child paid from HTTP `SUCCESS`. Existing completed evidence additionally requires parent `EXCHANGE_COMPLETED`, child/line delivered, exact exchange relation and delivered financial ledger. Reconciliation checks parent line, customer, receiving store/counter, replacement SKU/quantity and timing without any external call; it can then enable local-only finalization.
