## Concrete missing action found

At the review baseline, **manager return-window extension was missing**. This is a required code gap, rather than provider acceptance:

- `order/urls.py:43` mounts `AjaxExtendReturnView`; `order/views.py:4449–4479` selects the exact `(order_id,prod_id,has_product_id)` tuple, creates or updates its native extension, sets `is_active=1`, and records the mapped native administrator. The selected date ends at **23:59:59**. Updating can shorten an existing date or reactivate an inactive row. Empty input errors; the dialog's Cancel action does not clear native state.
- `order/templates/order/show.html:245–250` and `order/templates/order/online/_return_exchange_cells.html:49–54` expose **Extend Date** for roles **1, 2, 3** when the return reason says the window is closed. Their handlers submit the date at `show.html:1412–1473` and `online/show.html:1227–1287`. This is active UI, including online/other-store purchases.
- Baseline `return-workflow/repository.ts` read `ExtendApplicabilityForReturnExchange.extended_date` during admission, but the only application references to that table were its schema and this read. There was no extension writer, route or frontend control. Existing return tests could succeed by pre-seeding an extension; that did not implement the manager action.

The required fix is an exact-line manager action with fresh writer authorization and ordinary receiving-store/check-in/customer verification. A role-1 return override does not replace roles-2/3 extension. A generic table editor or direct source SQL instruction does not replace the workflow.

### Implementation follow-up

The owned implementation adds `return-workflow/extensions.ts`, registered GET/PUT `.../orders/:orderId/line-items/:lineId/return-window`, and `ReturnsPage`'s `ReturnWindowExtension` in both return and exchange modes. It reuses the existing native table; it creates no payment/refund migration or invented financial receipt.

GET/PUT require current roles 1–3, current store assignment/type/check-in/counter, the exact native order/HP/product relation, an unreturned delivered line, no active return/exchange operation, a live order/customer/contact-bound OTP proof, and an unambiguous native administrator mapping. Neither a cached manager role nor `created_by=0` substitutes for authority. Ambiguous native extension rows require reconciliation instead of updating arbitrary duplicates.

The date is strict ISO input in the business calendar, today or later, within native DATETIME storage. Native writes retain end-of-day `23:59:59`, preserve creation provenance on update, permit a deliberate shorter date, and reactivate an inactive tuple. The closed-window calculation controls the new UI action; an existing recorded date remains editable. Cancelling discards only the form. Other source eligibility/refund/stock checks still apply; changing a date neither accepts goods nor authorizes a cash refund.

PUT is natural desired-resource idempotency. An actor/scope/native-state-bound revision prevents overwriting a changed date from an old snapshot. An exact already-recorded desired date performs no extra write. Unknown replies and conflicts expose **Read recorded date**, with no automatic PUT, refund or warehouse retry. GET reports current recorded state, without claiming to prove which physical/user action happened. API responses/events contain opaque scope identifiers and date/state only, with no contact, code, raw native actor record, private revision in logs, or financial provider payload.

Validation: 15 focused checks pass (14 native checks and one literal-source oracle executing create/update/empty-date cases), five actual ReturnsPage Chromium workflows pass, and four existing return/exchange native regressions pass. Both scoped strict TypeScript configurations and scoped backend/frontend lint pass. Native checks use the real purpose-bound OTP service/queue/proof, current check-in/manager records, verified source table metadata, 20 exact retries, CAS conflicts, authority/contact revocation, and real return admission of only the extended duplicate-SKU HP. Browser API responses are synthetic; no warehouse/refund/provider is contacted. These are separate evidence edges and do not certify deployed warehouse/refund behavior.
