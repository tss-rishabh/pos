## Concrete controls missing at the frozen baseline

The active salesperson/cashier templates each expose CSV of visible columns and `colvis` (`report/templates/performance_report/{salesperson,cashier}_performance.html:130`); hyperlocal acceptance does too (`report/templates/orders/hyperlocal_order_accept_report.html:133`). At `fde67f5`, `performance.tsx:38` and `acceptance.tsx:21` mount `ReportView` without an export kind. The shared view renders all columns and has no visibility selector. Its queued-export schema has no performance/acceptance kind. These are missing executable features, despite an existing source calculation oracle and mapped `implementation_present` family.

Returned-orders and flash-sales source screens have both a visible-column CSV and a separate full export (`report/templates/orders/return_orders.html:150`, `report/templates/sales/index.html:180`). Their replacement offers the latter but omits column selection. Order transactions already has column visibility, but its sole export ignores that selection (`frontend/src/pages/operational-reports/order-transactions.tsx:111`); the source exposes both variants (`report/templates/orders/orders_data.html:395`). Performance/acceptance search is correctly absent: source `searching:false` is explicit, and the salesperson handler's read `search[value]` is unused.

The accompanying implementation closes these specific variants:

- The two performance reports and acceptance join the existing durable private export queue. Current manager authority is required at creation, build, recovery and download; restricted-manager assignments remain enforced, and an empty restricted selection stays empty.
- Source DataTable consumers of `ReportView` get visibility controls, initially showing all their original screen columns. Exports bind selected columns, submitted filters and sort/direction in the immutable command. No rows, customer fields or search text are persisted in the client's command marker.
- The requested replacement exports every matching row, bounded at 70,000 rows and the configured UTF-8 artifact byte budget. Original server-side DataTables' local CSV could export only its loaded page; the larger replacement scope is an explicit requirement, not a claim of identical original download bytes.
- Flash visible-column export uses the original **screen** query profile and its displayed district value. Existing unmarked full export keeps its distinct source joins and blank district CSV-key quirk. Order transactions retains a separate complete 75-column action; visible export binds its fixed `transaction_date DESC` ordering because the source screen disables ordering.
- Optional presentation fields have no defaults. Old unmarked export input hashes, report calculations and full CSV layouts remain unchanged. Both variants use existing conditional private upload, lost-PUT/HEAD recovery, worker leases and authenticated download rather than browser aggregation of giant result sets.

Implementation entry points are [export-domain.ts](../src/modules/operational-reports/export-domain.ts), [export-presentation.ts](../src/modules/operational-reports/export-presentation.ts), [export-service.ts](../src/modules/operational-reports/export-service.ts), [screen-report-csv.ts](../src/modules/operational-reports/screen-report-csv.ts), `frontend/src/pages/operational-reports/{report-view,performance,acceptance,order-transactions,export-commands}.tsx/ts`. No migration, new worker, external selector or route registrar is needed.

## Focused validation and practical limits

`tests/operational-reports/column-exports.test.ts` checks actual pinned template headings/controls, immutable old inputs, finite column/sort rejection, safe UTF-8 bounded CSV, complete global scores and refusal of oversized acceptance export. `export-mysql.integration.test.ts` covers a full 61-row manager artifact, changed-column command conflict, lost PUT→HEAD without requery/re-PUT, current role/store denial and empty restricted scope. Existing `mysql.integration.test.ts` retains actual source SELECT comparisons.

The actual-component runner `frontend/tests/operational-reports/column-browser.mjs` exercises the five shared report pages plus separate transaction visible/full actions against the backend builder. Warehouse facts and HTTP/storage are synthetic. The client retry tests prove lost responses reuse the exact sorted-column command and persist only UUID/digest metadata. These checks do not substitute for a deployed source→API→warehouse→worker→file workflow.

Focused result on Node 24.22.1: 35 backend checks across eight files (including 17 native checks on a dedicated digest-pinned MySQL 8.4.13 container), four client checks, six Chromium workflows with 61-row artifacts, both focused strict programs and changed-file ESLint passed. The broader production gate and external acceptance were not run by this change.
